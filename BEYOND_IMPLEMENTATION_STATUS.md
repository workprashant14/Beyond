## Windows run 3: `smallbody-stress.mjs` "pausing does not make it slower"

- **Root cause: unreliable test methodology, not the implementation.** `SmallBodies.tsx` calls `stepSlice`, which returns 0 immediately once a full cycle was evaluated for one clock value, so a paused layer does no position work (unit-tested in `tests/sliceupdate.test.ts`). Measured with CDP `ScriptDuration`: page JavaScript is about 100–120 ms/s running and about 45–55 ms/s paused (the remainder is the clock paint, the render loop and featured bodies). In a software-GL browser about 1000 ms of every second is CPU rasterisation of the 20,000 points, and that drifts between samples; the old test compared one 4 s running fps sample with one 2 s paused sample taken later, so the ≥0.9 ratio failed on noise alone (observed 19.4 vs 17.1 fps on Linux, and on Windows).
- **Fix (test only; threshold unchanged at 0.9):** five interleaved running/paused rounds in the same page, compared by median; plus a new direct assertion that paused JS time is ≤ 80% of running JS time. The guarantee "a settled layer does no expensive per-frame work" is now checked on the quantity that measures it.
- Linux: 5 consecutive focused runs all passed. Not verified on Windows by me.

## Windows run 4: small-body position cost while running at 100x

Reported: running 39.0 fps vs paused 49.2 fps, a 20.7% drop (limit 20%). Treated as a **real cost**, not noise: the test already uses interleaved medians.
- **What extra work runs at 100x:** the clock changes every frame, so the slice updater never settles. A full pass over 20,000 bodies took about 8–10 ms in Node, but the updater has a 3 ms per-frame budget and, when it finished a pass, immediately started another inside the same frame, so it spent the whole 3 ms **every** frame (about 15% of a 20 ms frame) plus the buffer upload. Per body it also recomputed time-independent maths (degree conversion, six trig calls for the orbit rotation, hypot and the visual scale).
- **Optimisation (same maths, same data):** `utils/smallBodyFast.ts` precomputes per-body constants once and warm-starts the Kepler solve from the previous frame (`E - M` offset), reusing sin/cos; `stepSlice` no longer starts a second pass inside one call. Node benchmark, one pass over 20,000 bodies: about 8 ms before, about 3 ms after. `tests/smallbodyfast.test.ts` checks it equals `smallBodyPosition` + `toScene` (closed and open orbits, 3000 consecutive 17-day frames, across the 2π wrap, e up to 0.99).
- **Accuracy bug found on the way and fixed:** `solveKepler` (shared) did not converge for some mean anomalies when e ≥ 0.8 (measured over a 20,000-point M sweep: failures for 0.1% of M at e = 0.8, 0.7% at e = 0.9, 9% at e = 0.99), so high-eccentricity comets could be drawn in wrong places. It is now a bracketed (safeguarded) Newton; results for e < 0.8 are unchanged and every existing orbit oracle test still passes. Regression test added.
- Threshold (20%) and assertions unchanged.
